Bug Report: BetterYourAds v4

Purpose:
This report records the bugs found during the dev branch audit of the last 8 merge tags and last 15 commits.

Bug:
Inline ad prompt and render requests can attach records to an unverified saved ID.

File:
apps/backend/src/routes/ad-prompt.ts
apps/backend/src/routes/render.ts
apps/backend/tests/ad-prompt.routes.test.ts
apps/backend/tests/render.routes.test.ts

Why it is a bug:
The ad-prompt route accepted both an inline brandExtraction payload and a brandExtractionId. When both were present, it skipped the ownership lookup because the inline payload already existed, then saved the new ad prompt with the supplied brandExtractionId.

The render route had the same pattern for inline adPrompt plus adPromptId. It skipped the ownership lookup and then persisted the generated ad with the supplied adPromptId.

This meant a user could submit their own inline payload while attaching the resulting row to a saved brand or prompt ID that was missing, foreign, or otherwise not owned by them. The database foreign key would still reject truly missing IDs, but it would not stop cross-user references unless the route checked ownership first.

How to reproduce:
1. Sign in as user A.
2. Send POST /api/ad-prompt with a valid inline brandExtraction and a brandExtractionId belonging to user B.
3. Observe that the route can proceed without checking that user A owns the brandExtractionId.
4. Send POST /api/render with a valid inline adPrompt and an adPromptId belonging to user B.
5. Observe that the route can proceed without checking that user A owns the adPromptId.

Expected fix:
Always validate any supplied brandExtractionId or adPromptId against the authenticated user, even when an inline payload is supplied. Only use the saved row as the payload fallback when the inline payload is missing.

Risk level:
P1

Suggested test:
Add route tests where an inline payload is supplied together with a missing or foreign ID. Assert that the route returns 422, never calls the pipeline, and never persists the row.

Fix applied:
apps/backend/src/routes/ad-prompt.ts now calls getBrandExtraction(brandExtractionId, userId) whenever brandExtractionId is supplied.
apps/backend/src/routes/render.ts now calls getAdPrompt(adPromptId, userId) whenever adPromptId is supplied.
Regression tests were added for both routes.

Bug:
Admin user deletion can fail on fresh setups because the cleanup flow expects a legacy brand-assets bucket.

File:
apps/backend/src/services/supabase.ts
apps/backend/tests/supabase.persistence.test.ts
supabase/schema.sql

Why it is a bug:
The deleteUser flow cleans files from both the ads bucket and the brand-assets bucket before deleting the auth user. That is correct for installs that previously used browser-uploaded brand assets.

However, the current paste-once supabase/schema.sql only created the active ads bucket and did not create the legacy brand-assets bucket/table. On a fresh setup following the current schema snapshot, deleting a user could fail while listing the absent brand-assets bucket. That would leave the account undeleted even though the missing bucket is not required by the current web flow.

How to reproduce:
1. Create a fresh Supabase project using the current supabase/schema.sql.
2. Do not create the brand-assets bucket.
3. Create and approve a user.
4. Delete that user through the admin dashboard or DELETE /api/admin/users/:id.
5. Observe the deletion failing when backend cleanup tries to list brand-assets.

Expected fix:
Treat brand-assets as an optional legacy cleanup target. If the bucket is absent, continue deletion after successfully cleaning the required ads bucket. Also update supabase/schema.sql so a fresh setup includes the legacy brand_assets table and brand-assets bucket for compatibility with older data paths.

Risk level:
P2

Suggested test:
Add a deleteUser persistence test where ads cleanup succeeds and brand-assets listing returns a 404 bucket-not-found error. Assert that auth.admin.deleteUser is still called.

Fix applied:
apps/backend/src/services/supabase.ts now ignores missing-bucket errors only for optional cleanup targets.
supabase/schema.sql now creates the legacy brand_assets table, brand-assets bucket, and scoped storage policies.
Regression coverage was added in apps/backend/tests/supabase.persistence.test.ts.
